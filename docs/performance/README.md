# Производительность и воспроизведение

Базовый релиз — NGINX 1.31.8, коммит `140aa942711868a8daeb95810bc9a81f272ada72`. Прежняя версия форка `6f5052f` уже содержит SSE2-парсер заголовков и оптимизацию upstream random. Снимок `65284d1` добавил ARM NEON, обработку хвоста URI и экранирования, а также `-O2` по умолчанию. Приведённые ниже сквозные измерения сделаны до последующего исправления проверки единичных весов. В нагрузочных тестах прокси использовался один backend с обычным round robin. [Релиз](https://github.com/nginx/nginx/tree/140aa942711868a8daeb95810bc9a81f272ada72) · [Две ревизии форка](https://github.com/SemyonDerduga/nginx/compare/6f5052f0377d12286e8432ac1916c5d32f4c99c0...65284d1bb40196e8dc62e5b8ea75e8dfa6188faf)

Для ветки добавлена [проверка правильности на x86-64 и ARM64](../../.github/workflows/perf-regressions.yml). Она собирает релиз и форк с одинаковыми параметрами, запускает закреплённые официальные тесты, проверяет переполнение весов на реальном процессе и сравнивает ответы и логи. Для воспроизведения прежнего сравнения производительности на Linux есть [команды и CSV](audit/README.md).

## Изменения в коде

| Изменение | Когда выполняется |
| --- | --- |
| Значения заголовков HTTP/1 | SSE2 или NEON сканирует 16 байт за итерацию до первого байта ≤ 0x20. Штатный автомат обрабатывает найденный байт и короткий остаток. Это используется и для ответа HTTP/1 от upstream. |
| Хвост URI | В состоянии `sw_uri` парсер ищет байты ≤ 0x20, DEL и `#`. В эту ветвь попадает, в частности, query string. |
| Экранирование в access log | При подсчёте длины для обычного и JSON-формата пропускаются чистые блоки. После блока со спецсимволом подсчёт продолжается скалярно. Запись самих символов выполняет исходный код. |
| Флаги GCC и Clang | При штатном выборе флагов сборка форка использует `-O2`, релиз использует `-O`. Переданные через `--with-cc-opt` флаги добавляются в конце. При заданной переменной `CFLAGS` сборка использует её значение. Эффект для готового пакета зависит от флагов его сборки. |

Реализации SIMD выбираются при компиляции. На платформах без поддерживаемых инструкций сохраняется скалярный путь. [SIMD](../../src/core/ngx_simd.h) · [Парсер](../../src/http/ngx_http_parse.c) · [Обычный лог](../../src/http/modules/ngx_http_log_module.c) · [JSON](../../src/core/ngx_string.c) · [Выбор флагов](../../auto/cc/conf)

## Linux x86-64

В первой серии сравнивались релиз и один патч SSE2 для значений заголовков (`2dbc6a0`). На AMD EPYC 9V74 с GCC 14.2 один worker обслуживал HTTP/1.1 по loopback без TLS и access log. Генератор и backend были закреплены за отдельными CPU. Восемь пар по 1,5 с на вариант дали 8 696 915 проверенных ответов. Медиана парного изменения RPS для Cookie из 2 048 одинаковых байтов составила **+15,9%** при прямом ответе и **+12,0%** через прокси. Для коротких и смешанных заголовков медианы от −1,3% до +1,9% укладывались в наблюдавшийся разброс A/A. [Прогоны A/B](throughput/results/e2e.csv) · [Прогоны A/A](throughput/results/aa.csv)

Вторая серия прошла на VM с Intel Xeon Platinum 8573C, Linux 6.18.57, GCC 14.2 и девятью доступными логическими CPU. Использовались HTTP/1.1, один frontend, отдельные CPU для клиента и backend, 12 соединений и проверка статуса, длины и тела `OK`. В сценариях Host, браузерных заголовков и query включён обычный лог с буфером 64 КиБ. При тестировании Cookie лог выключен. За 216 прогонов по 1,1 с обработано 14 485 710 ответов. | --- | ---: | ---: | ---: |
| Прямой ответ, Host | −1,3% | −0,6% | +1,5% |
| Прокси, браузерные заголовки | +7,4% | +0,8% | +12,8% |

| Прокси, Cookie 2 КиБ | +6,6% | +3,2% | +16,4% |

После выброса в контрольной серии A/A старый и новый форки дополнительно сравнили при одинаковом `-O2` в 36 прогонах по 2 с. Для длинного query с JWT RPS вырос на **9,2%** (диапазон +1,5…+10,4%, 6/6 пар), а CPU фронта на запрос снизился на **9,5%**. Для браузерного прокси медиана RPS составила +0,4%, диапазон −17,4…+48,2%, ускорение в 3/6 пар. Для длинного query без JWT медиана составила +14,0%, диапазон −5,9…+28,0%, ускорение в 5/6 пар. [Основная серия](audit/results/linux.csv) · [Повтор](audit/results/confirm.csv) · [Команды для этой серии](audit/README.md)

При фиксированных 25 000 запросов/с отдельное сравнение релиза с `65284d1` (оба `-O2`) дало для Cookie 2 КиБ медиану парных изменений p50 −1,28 мкс и p99 +724 мкс. Направление изменения p99 менялось. Результат зависит и от планирования генератора в общей VM. Серии измеряли синтетические HTTP/1-нагрузки на loopback. Данных о p99 под производственным трафиком, TLS, HTTP/2, HTTP/3 и потреблении памяти серверами здесь нет.

## Apple M3 Pro

В архиве две независимые серии на macOS. Один процесс frontend без master обслуживал прямой ответ или проксировал на второй NGINX с `keepalive 64`. Генератор ApacheBench использовал `-k -c 32`. На клиентском плече стандартный `ab` отправляет HTTP/1.0 с keepalive, при отсутствии ручных заголовков также добавляет Host, User-Agent, Accept и Connection. NGINX обращается к backend по HTTP/1.1. CPU/запрос — прирост пользовательского и системного CPU-времени фронта по `ps`, делённый на число завершённых запросов. RPS относится ко всему стенду. Клиент, ядра разных классов, планировщик и температурный режим могут влиять на результаты. Точные версии macOS, Apple Clang и `ab`, объём RAM, состояние системы, привязка к ядрам и полные команды исторической сборки не сохранены. [Стенд](arm64/bench.py) · [Формирование запроса в ApacheBench](https://github.com/apache/httpd/blob/2.4.x/support/ab.c#L1874-L1927)

**Парсер заголовков и буферизация лога.** Шесть раундов по 5 с с `-O2`, обычный лог с полем `$request_time`. В таблице медианы изменений CPU фронта на запрос относительно исходного варианта без буфера. В третьем столбце указаны минимум и максимум для патча парсера.

| Нагрузка | NEON | Диапазон NEON | Только настройка `buffer=64k flush=1s` |
| --- | ---: | ---: | ---: |
| Прокси, браузерные заголовки | −3,2% | −21,9…+20,7% | −20,5% |
| Прокси, Cookie 2 КиБ | −5,7% | −12,1…+2,3% | −22,3% |
| Прямой ответ, Cookie 2 КиБ | −16,2% | −32,6…−10,2% | −37,8% |

В A/A для браузерного прокси отдельные пары показали от −20,1% до +21,5% CPU/запрос. Эффект NEON через прокси на этом стенде остаётся неопределённым. Для буфера все шесть пар дали экономию во всех трёх сценариях. В записи о профилировании под нагрузкой упоминаются стеки `writev`, `recvfrom` и `write`. Исходные выборки `sample` отсутствуют, поэтому долю активного CPU в каждой функции по архиву установить нельзя. [Сводка](arm64/results/m3pro.txt) · [Конфигурации и запросы](arm64/spec.json)

**Все изменения и флаги компиляции.** Восемь раундов по 4 с, у всех вариантов обычный access log с буфером 64 КиБ. Дельты в таблице рассчитаны относительно исходного релиза с `-O`.

| Нагрузка | CPU/запрос, релиз `-O2` | CPU/запрос, форк `-O2` | Диапазон пар для форка |
| --- | ---: | ---: | ---: |
| Прокси, браузерные заголовки | −0,7% | −3,9% | −10,3…+35,2% |
| Прямой ответ, query 458 Б, токен 673 Б и браузерные заголовки | −5,4% | **−25,1%** | −32,9…−17,1% |
| Прямой ответ, без заданных пользователем заголовков | −0,8% | −2,1% | −30,8…+1,2% |

Для длинного запроса медианный парный прирост RPS к релизу с `-O` составил **+33,2%**. При одинаковом `-O2` сохранены только отдельные медианы — 131 836 и 167 272 RPS, 7,36 и 5,78 мкс CPU на запрос. Их отношения дают +26,9% и −21,5%. Вычислить парный эффект при одинаковых флагах из этой исторической сводки нельзя. Разброс коротких запросов также не позволяет исключить регрессию. Нативного повтора на M3 во время независимой проверки не было. [Сводка](arm64/results/m3pro-universal.txt) · [Конфигурации и запросы](arm64/spec-universal.json)

На Linux переключение буфера access log в одной и той же сборке `65284d1` дало −5,4% CPU/запрос для Host, −5,7% для браузерного прокси и −8,3% для прямого длинного query с JWT. Эффект зависит от файловой системы и объёма записей. Буферизация откладывает видимость строк до заполнения буфера или его сброса по таймеру. При аварии воркера можно потерять ещё не записанные строки. [Прогоны](audit/results/logbuffer.csv)

## Балансировщик и keepalive

Для `random` и `random two` прямой индекс допустим, когда **каждый фактический вес равен 1**. Модуль устанавливает этот признак во время построения или обновления таблицы диапазонов. Для остальных весов сохраняется двоичный поиск, в том числе если сумма весов переполнилась. В `65284d1` проверка `peers->weighted` могла ошибочно включить оптимизацию для трёх весов `INTPTR_MAX, INTPTR_MAX, 5`. Исправление сохраняет поведение базового релиза при такой сумме. Для 9 840 обычных наборов весов (длины 1–8, веса 1–3) совпали 147 624 выбора. При 256 узлах с весом один пропускаются восемь сравнений. Сквозной RPS для этой оптимизации не измерялся. [Модуль](../../src/http/modules/ngx_http_upstream_random_module.c) · [Проверка](upstream/check_random.py)

В штатном NGINX один клиент последовательно обходил 33 backend-адреса с обычным round robin. После прогрева пул на 32 записи открыл 264 новых TCP-соединения на 264 запроса. Установка `keepalive 64 local;` в том же `upstream` устранила все 264 открытия. Это настройка пула на worker. Требуемая ёмкость и расход памяти зависят от числа адресов, параллелизма и числа workers. [Модуль keepalive](../../src/http/modules/ngx_http_upstream_keepalive_module.c) · [Наблюдаемые соединения](upstream/observed.json)

## Сборка и проверки на Linux

Команды выполняются из корня форка на Linux с GCC, make, Perl, Python 3, заголовками OpenSSL, zlib и PCRE2. Для сравнения кода используются одинаковые флаги. Полный набор nginx-tests дополнительно зависит от собранных модулей, прав на создание сокетов, доступной сети и установленных Perl-модулей.

```sh
git switch perf/1.31.8
git worktree add --detach ../nginx-base 140aa942711868a8daeb95810bc9a81f272ada72
for tree in . ../nginx-base; do
  (cd "$tree" && auto/configure --with-http_ssl_module --with-http_v2_module --with-stream --with-threads --with-cc-opt="-O2 -g -fno-omit-frame-pointer" && make -j4) || exit 1
done
git clone https://github.com/nginx/nginx-tests.git ../nginx-tests
git -C ../nginx-tests checkout --detach 16964ee752509eb6271c4e8760e7899274240755
bash docs/performance/check.sh ../nginx-tests "$PWD/objs/nginx"
```

`check.sh` выбирает 12 файлов. В расширенной независимой проверке релиза и снимка `65284d1` конечные статусы всех 512 файлов совпали. Для каждой сборки 334 файла прошли, 172 пропущены, 6 завершились ошибкой. Из 5 094 TAP-проверок — 4 949 PASS, 85 SKIP, 43 TODO, 17 неуспешных. Пять проблемных файлов использовали недоступные в окружении UNIX-сокеты, в шестом ОС немедленно вернула `Network is unreachable` вместо ожидаемого тайм-аута.

Полный повтор для релиза и сборки с исправленной проверкой единичных весов проведён с расширенным набором зависимостей. Конечные статусы каждого из 512 файлов снова совпали. Для каждой сборки 335 файлов прошли, 171 пропущен, 6 с ошибками. Из 5 098 TAP-проверок — 4 950 PASS, 88 SKIP, 43 TODO и 17 неуспешных. [Официальный набор](https://github.com/nginx/nginx-tests/tree/16964ee752509eb6271c4e8760e7899274240755)

На x86-64 отдельно проверены 65 536 масок, 211 165 случаев строки запроса, 148 723 случая заголовков и 1 719 042 сравнения экранирования с ASan/UBSan и защитой границ памяти. На AArch64 в эмуляторе Unicorn сравнили парсер с релизом в 46 080 случаях для каждой из восьми комбинаций GCC 14.2 / Clang 18.1.6, little-endian / big-endian, NEON / скалярный код. На четырёх SIMD-сборках проверены все 65 536 масок двух предикатов. Эти запуски проверяют корректность.

```sh
LAB=docs/performance
BASE=$(realpath ../nginx-base/objs/nginx)
CANDIDATE=$(realpath objs/nginx)
mkdir -p rerun
python3 "$LAB/parser/prepare.py" ../nginx-base .
cc -O2 -Wall -Wextra "$LAB/parser/compare.c" -o rerun/parser-check
rerun/parser-check
python3 "$LAB/upstream/check_random.py" ../nginx-base .
python3 "$LAB/upstream/check_random_routing.py" "$BASE" "$CANDIDATE"
```

Автономный тест парсера использует минимальные структуры. Для проверки с типами NGINX добавьте `-DUSE_NGINX_HEADERS`, `-Iobjs` и пути из `objs/Makefile`. Сетевой фаззер сравнивает HTTP-ответы и два access log. Для отклонённых запросов граница чтения может менять длину записанного фрагмента уже в базовом NGINX. В независимом сравнении на 5 000 входов HTTP-ответы совпали. В прогоне с одинаковой доставкой совпали и оба лога по 5 017 строк. Обновлённый фаззер воспроизвёл один корпус из 5 000 входов (`SEED=11192026`) под Python 3.11 и 3.12. При фрагментированной и при заранее поставленной в очередь доставке ответы совпали. В режиме с управляемой доставкой сравнились и оба лога, по 5 019 строк в каждом. [Фаззер](parser/difffuzz.py)

## Воспроизведение нагрузки

**Linux.** Для пяти профилей первой серии соберите штатные клиенты стенда и выполните команды ниже. Они измерят вашу текущую ветку относительно релиза. Для исторического сравнения только патча SSE2 используйте отдельную сборку `2dbc6a0af4edc36597fa54274837bebd3e7939ed`. Клиент проверяет статус, размер и тело ответа. Throughput требует как минимум три доступных логических CPU. При измерении задержки сохраняются времена запланированной и фактической отправки и завершения запроса.

```sh
cc -O2 -pthread "$LAB/throughput/load.c" -o "$LAB/throughput/load"
cc -O2 "$LAB/latency/rate.c" -o "$LAB/latency/rate"
python3 "$LAB/throughput/run.py" "$BASE" "$CANDIDATE" --output rerun/e2e.csv
python3 "$LAB/throughput/run.py" "$BASE" "$BASE" --ctrl --rounds 4 --seconds 1 --output rerun/aa.csv
python3 "$LAB/throughput/summarize.py" rerun/e2e.csv
python3 "$LAB/latency/run.py" "$BASE" "$CANDIDATE" --out rerun/latency
python3 "$LAB/latency/summary.py" rerun/latency/fixed.csv
```

**macOS на Apple Silicon.** Для нового опыта с тремя вариантами нужны собственные ARM64-сборки, Xcode Command Line Tools, PCRE2, Python 3 и ApacheBench. Запустите команды из клона в нативной arm64-сессии. `WORK` должен быть новым каталогом без пробелов. Вывод конфигуратора и Makefile сохранят фактические флаги каждого бинарника.

```sh
set -e
export WORK="$(mktemp -d)"
mkdir -p "$WORK/objs"
git worktree add --detach "$WORK/upstream" 140aa942711868a8daeb95810bc9a81f272ada72
git worktree add --detach "$WORK/fork" HEAD
build() (
  cd "$1"
  builddir="$WORK/objs/$2"
  shift 2
  unset CFLAGS
  auto/configure --with-cc=clang --builddir="$builddir" "$@" >"$builddir.configure.log"
  make -j4 >"$builddir.make.log"
)
build "$WORK/upstream" b-dflt
build "$WORK/upstream" b-O2 --with-cc-opt=-O2
build "$WORK/fork" c-dflt
file "$WORK"/objs/*/nginx
python3 docs/performance/arm64/bench.py docs/performance/arm64/spec-universal.json \
  --output "$WORK/rounds.csv"
```

Скрипт сохраняет завершённые запуски каждого варианта и рядом файл `rounds.csv.metadata.json` с конфигурацией, версиями ApacheBench и NGINX, параметрами ОС, CPU и RAM на macOS. В CSV указаны номер раунда, порядок внутри него, число запросов, RPS и CPU-время. Сводка сравнивает каждую пару вариантов, включая релиз и форк при `-O2`. Чередование с разворотом и поворотом порядка распределяет позиции между вариантами. Для A/A задайте две записи с одним бинарником и одинаковой конфигурацией. Исторический `spec.json` использует имена `base-full` и `cand-full` для отдельного опыта с буферизацией и патчем заголовков. Подставьте соответствующие пути в собственную копию спецификации.

ApacheBench хранит статистику по запросам в памяти клиента. Ёмкость по умолчанию составляет 5 млн запросов на запуск, что при 32 байтах на запись требует около 153 МиБ виртуального пространства для массива. При достижении лимита скрипт прерывает сравнение. Для более длинного интервала установите `--max-requests` с учётом RPS и доступной памяти. Следите также за объёмом временных логов, особенно при длинном URI. В истории использовался лимит 100 млн запросов.

## Гипотезы для следующих экспериментов

При сборке запроса к backend модуль proxy повторно ищет заголовки-исключения. Для TLS можно исследовать копирование полного буфера с учётом повторной записи, для файлового кеша — конкуренцию за mutex при росте числа workers. Для этих трёх направлений сквозного замера пока нет.
