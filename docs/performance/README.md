# Производительность и воспроизведение

База — [официальный NGINX 1.31.8](https://github.com/nginx/nginx/commit/140aa942711868a8daeb95810bc9a81f272ada72). В [HTTP/1-парсере](../../src/http/ngx_http_parse.c) SSE2 на x86-64 или NEON на aarch64 просматривает по 16 байт значения заголовка, пока не встретится байт ≤ 0x20. Штатный автомат обрабатывает этот байт и короткий остаток. В [модуле upstream random](../../src/http/modules/ngx_http_upstream_random_module.c) при единичных весах всех серверов (флаг `peers->weighted`, который NGINX уже поддерживает при изменении состава серверов) результат случайной выборки уже равен индексу. Смешанные веса используют исходный двоичный поиск.

## Сквозной эксперимент с парсером

Linux x86-64, AMD EPYC 9V74, GCC 14.2, один worker NGINX. Клиент и HTTP-бэкенд закреплены за другими CPU на той же машине. HTTP/1.1 keepalive, loopback, ответ 200 с двухбайтовым телом, без TLS и access log. Восемь пар по 1,5 с на вариант с чередованием порядка. Приведены медианы парных относительных изменений; во всех пяти сценариях проверено 8 696 915 ответов. В этой серии был включён только патч парсера.

| Запрос | Прямой ответ | Reverse proxy |
| --- | --- | --- |
| Только Host | +1,9% (5/8 пар) | — |
| Host, User-Agent, Accept, Accept-Encoding и небольшая Cookie | −1,3% (2/8) | +1,1% (5/8) |
| Host и Cookie из 2 048 одинаковых байтов без пробелов | +15,9% (7/8) | +12,0% (8/8) |

Контроль A/A из четырёх пар на сценарий дал разброс отдельных сравнений от −9,9% до +7,4%. На коротких заголовках выигрыш не установлен. При фиксированных 25 000 запросов/с с длинной Cookie p50 снизилась с 18,29 до 14,12 мкс. Улучшение p99 не подтвердилось. Условия теста благоприятны для SIMD. Профили HTTP/2 и HTTP/3, TLS и сетевой трафик рабочих сервисов в эти замеры не входили.

## Проверка балансировщика и keepalive

На 9 840 наборах весов длиной 1–8, с весами 1–3, все 147 624 результата выбора совпали. При 256 серверах с весом один исключаются восемь сравнений в таблице диапазонов, остаётся проверка флага. На фоне вызова `ngx_random()` это доли наносекунды; сквозной RPS для этого изменения не измеряли.

В штатном NGINX один клиент последовательно обходил 33 backend-адреса с обычным round robin. После прогрева пул на 32 записи открыл 264 новых TCP-соединения на 264 запроса; установка `keepalive 64 local;` в том же `upstream` устранила все 264 открытия. Это наблюдение о конфигурации. Полезная ёмкость пула зависит от параллелизма, числа воркеров и порядка обращений. [Исходники keepalive](../../src/http/modules/ngx_http_upstream_keepalive_module.c)

## Сборка и тесты

Из корня клона выполните команды на Linux с GCC, make, Perl, заголовками OpenSSL, zlib и PCRE2. Файл `auto/configure` находится в Git-репозитории. Для тестов используются локальные временные серверы.

```sh
git switch perf/1.31.8
git worktree add --detach ../nginx-base 140aa942711868a8daeb95810bc9a81f272ada72
for tree in . ../nginx-base; do
  (cd "$tree" && auto/configure --with-http_ssl_module --with-http_v2_module --with-cc-opt="-O2 -g -fno-omit-frame-pointer" && make -j4) || exit 1
done
git clone https://github.com/nginx/nginx-tests.git ../nginx-tests
git -C ../nginx-tests checkout --detach 16964ee752509eb6271c4e8760e7899274240755
bash docs/performance/check.sh ../nginx-tests "$PWD/objs/nginx"
```

На объединённой сборке выполнено 283 проверки из 12 официальных файлов: 280 прошли, три дали ожидаемый для этой версии результат TODO. Неожиданных отказов и пропусков нет. Отдельный корпус парсера прошёл 213 420 сравнительных случаев, включая 29 580 случаев с защищённой страницей после буфера.

## Нагрузочный стенд и данные

Из корня форка после сборки создайте новый каталог для результатов, скомпилируйте оба клиента и запустите парные измерения. Укажите свободные CPU и используйте машину без конкурирующей нагрузки. Архивные проценты относятся к сборке с одним патчем парсера `2dbc6a0af4edc36597fa54274837bebd3e7939ed`; команды ниже проверяют текущую ветку с двумя патчами. В наборе нагрузок используется один upstream с обычным round robin, поэтому режим random в этом тесте не задействован.

```sh
LAB=docs/performance
BASE=$(realpath ../nginx-base/objs/nginx)
CANDIDATE=$(realpath objs/nginx)
mkdir -p rerun
cc -O2 -pthread "$LAB/throughput/load.c" -o "$LAB/throughput/load"
cc -O2 "$LAB/latency/rate.c" -o "$LAB/latency/rate"
python3 "$LAB/throughput/run.py" "$BASE" "$CANDIDATE" --output rerun/e2e.csv
python3 "$LAB/throughput/run.py" "$BASE" "$BASE" --ctrl --rounds 4 --seconds 1 --output rerun/aa.csv
python3 "$LAB/throughput/summarize.py" rerun/e2e.csv
python3 "$LAB/latency/run.py" "$BASE" "$CANDIDATE" --out rerun/latency
python3 "$LAB/latency/summary.py" rerun/latency/fixed.csv
```

Исходные агрегаты по каждому запуску: [A/B](throughput/results/e2e.csv), [A/A](throughput/results/aa.csv), [фиксированная нагрузка](latency/results/fixed.csv). Клиенты проверяют статус, длину и тело ответа. При фиксированной нагрузке сохраняются отдельные времена запланированной отправки, фактической отправки и завершения запроса.

## arm64: профиль и буфер access log

Apple M3 Pro, macOS, clang, `-O2`, один worker без master. Фронтовой NGINX проксирует на второй NGINX через `keepalive 64`, пишет access log в формате `combined` с `$request_time`. Нагрузка — `ab -k -c 32`, по 5 с на вариант, 6 пар с чередованием порядка. Метрика — CPU воркера на запрос (user+sys из `ps`): она не зависит от того, упирается ли однопоточный `ab` в свой предел. Ноутбук шумный, контроль A/A даёт отдельные пары до ±20%, поэтому выводы опираются на медиану и знак всех пар.

Профиль `sample` под нагрузкой с типичными браузерными заголовками: около 75% времени воркера занимают системные вызовы (`writev`, `recvfrom`, `write`). Из них примерно 23% — `write()` access log, по одному на запрос. `ngx_http_parse_header_line` — около 5%, `ngx_hash_find` — 1,3%, экранирование переменных лога и сборка запроса к upstream — меньше 1% каждое.

| Сценарий | NEON-патч, CPU/запрос | `buffer=64k flush=1s`, CPU/запрос |
| --- | --- | --- |
| Прокси, типичные заголовки | −3% (в пределах шума) | −20% |
| Прокси, Cookie 2 КиБ | −6% | −22% |
| Прямой ответ, Cookie 2 КиБ | −16% (все пары) | −38% |

[Сырые результаты](arm64/results/m3pro.txt) · [скрипт](arm64/bench.py) · [варианты](arm64/spec.json)

Вывод: при логе без буфера каждый запрос платит за отдельный `write()`, и это дороже всего парсера. Буфер откладывает запись строк до 1 с или 64 КиБ; цена — при аварийном завершении воркера теряется хвост лога.

NEON-ветка повторяет SSE2-ветку: `vcleq_u8` отмечает байты ≤ 0x20, `vshrn_n_u16` сжимает 16 флагов в 64-битную маску по 4 бита на байт. Обе ветки вынесены в `ngx_http_parse_ctl_offset()`.

### Дифференциальный фаззер

[`parser/difffuzz.py`](parser/difffuzz.py) запускает базовую и патченую сборку за одним echo-бэкендом и шлёт одинаковые запросы: случайные значения заголовков (управляющие байты, `\0`, `\x7f`, байты ≥ 0x80, длины около границ 16 байт), случайные точки разреза TCP, `client_header_buffer_size 64`, чтобы строки пересекали буферы. Бэкенд возвращает сырой запрос и случайный заголовок ответа, так что сравнивается и разбор ответа upstream.

```sh
python3 docs/performance/parser/difffuzz.py ../nginx-base/objs/nginx objs/nginx 3000
# x86-64 под Rosetta: добавьте четвёртым аргументом x86_64
```

Результат: 0 расхождений на 5 000 случаях NEON (arm64) и 5 500 случаях SSE2 (x86-64 под Rosetta). Чувствительность проверена мутантами со сдвигом позиции на один байт: 398 расхождений из 1 500 (SSE2) и 272 из 1 000 (NEON).

## Универсальные ускорения

Правки, которые не требуют настройки и не меняют поведение. Общие 16-байтовые примитивы (SSE2 на x86-64, NEON на aarch64) вынесены в [`src/core/ngx_simd.h`](../../src/core/ngx_simd.h). На других платформах остаётся прежний скалярный код; сборка с `-U__ARM_NEON` проверена.

| Изменение | Где помогает |
| --- | --- |
| `-O2` вместо `-O` по умолчанию для gcc и clang (`auto/cc/gcc`, `auto/cc/clang`) | Сборки из исходников без `--with-cc-opt`. Пакеты nginx.org и дистрибутивов уже собираются с `-O2`, а явный `--with-cc-opt` по-прежнему имеет приоритет. |
| SIMD для значений заголовков (запрос и ответ upstream) | Длинные Cookie, `Authorization: Bearer <JWT>`, Referer, Accept. |
| SIMD для хвоста URI в строке запроса (обычно query string) | UTM-метки, `gclid`, токены в URL. Пропускаются блоки без байтов ≤ 0x20, DEL и `#`; остальное разбирает прежний автомат. |
| SIMD при подсчёте экранирования в access log (`escape=default` и `escape=json`) | Каждая строка лога с `$http_user_agent`, `$http_referer`, `$request`. Чистые блоки пропускаются, при первом спецсимволе работает прежний цикл. |

Замер на M3 Pro: 8 пар по 4 с, лог с `buffer=64k`, чтобы системные вызовы меньше маскировали код. Δ — медиана парных изменений CPU на запрос относительно базы с `-O`.

| Сценарий | База `-O2` | Все правки |
| --- | --- | --- |
| Прокси, типичные браузерные заголовки | −0,7% | −3,9% (в пределах шума) |
| Прямой ответ, query string 400 Б + JWT 800 Б + браузерные заголовки | −5,4% | **−25,1%**, все 8 пар от −17% до −33%, RPS +33% |
| Прямой ответ, только Host | −0,8% | −2,1%, регрессии нет |

[Сырые результаты](arm64/results/m3pro-universal.txt) · [варианты](arm64/spec-universal.json)

Корректность: [дифференциальный фаззер](parser/difffuzz.py) теперь варьирует URI и query string и сравнивает построчно оба access log (обычный и `escape=json`). На финальном коде 0 расхождений: 3 000 случаев на arm64 и 2 000 на x86-64. Мутанты, отключающие по одному условию в каждом быстром пути (DEL в URI, `"` в логе, `\` в JSON), фаззер ловит.

Что проверено и отклонено:

- **Буфер access log по умолчанию.** Самый большой выигрыш (−20…−38%), но меняет поведение: строки лога пишутся с задержкой и теряются при аварии воркера. Оставлено настройкой.
- **Двойной поиск исключений в `ngx_http_proxy_create_request`**, **поиск браузера по User-Agent** (до шести `ngx_strstrn`), **кеширование пулов и буфера заголовков между запросами keepalive**. Каждое меньше 1% CPU в профиле, а правка заметно усложняет код или меняет расход памяти.
- **Имена заголовков.** Хеш считается последовательно по байтам, SIMD здесь неприменим без смены хеш-функции.

## Гипотезы для следующих экспериментов

В `ngx_http_proxy_create_request` повторяется поиск исключений по заголовкам при расчёте длины и сериализации. В TLS можно исследовать пропуск копии полного буфера при сохранении семантики повторной записи. У файлового кеша стоит измерить конкуренцию за mutex при росте числа workers. Для этих трёх гипотез сквозной выигрыш ещё предстоит измерить.
